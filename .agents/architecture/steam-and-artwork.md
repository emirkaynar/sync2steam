# Steam and artwork architecture

Status: proposed for the Windows 11 MVP, 2026-11-21. The [Steam research](../research/steam.md) records verified upstream behavior and open questions. The integration targets a selected local Steam profile and works with the network unavailable. SteamGridDB is the primary provider when artwork acquisition is enabled.

## Boundaries and data flow

| Component | Responsibility |
| --- | --- |
| Steam discovery | Find and validate installation and profile candidates, report provenance, and pin the user-selected destination |
| Steam compatibility adapter | Read binary VDF, map the three shortcut ID representations, render precise record changes, map grid filenames and optionally prepare static collection patches |
| Reconciliation planner | Compare canonical game identities, launch variants, desired artwork and previous ownership against the selected profile snapshot. Produce a reviewable change set |
| Apply and recovery | Fence concurrent producers, check inputs again, stage, back up, journal, replace, verify and recover |
| Launch dispatcher | Resolve one opaque shortcut token to an approved local executable or provider action and execute it in the user’s session |
| Artwork service | Resolve title matches, import or download optional assets, validate and cache them, and supply staged files to the planner |

Scanning and preview are read-only with respect to Steam. Cache and journals live in application directories outside Steam. Apply, rollback and the optional restart have separate outcomes. The preview names the Steam root and account, summarizes add/update/remove, artwork and collection changes, and shows collisions, blocked inputs and external edits. A stale or profile-mismatched plan must be regenerated.

## Discovery and profile isolation

1. Validate an explicit root first if configured, then inspect read-only Windows registry candidates. Use current-user `SteamPath` and machine `InstallPath` in explicit registry views. Use the default Program Files (x86) path as a final candidate and offer a folder picker.
2. Canonicalize candidates, collapse equivalent roots, and require a plausible client root with `steam.exe` and `userdata`. Report ambiguity if multiple valid roots survive. Treat additional Steam libraries as inventory hints.
3. Read text `config/loginusers.vdf` as optional metadata and enumerate existing nonzero numeric `userdata` directories. Correlate SteamID64 to account ID using exact arithmetic and keep the numeric directory as the configuration target. Allow an orphan or fresh profile only if it is already an existing, valid user directory and is selected explicitly. Missing or damaged login metadata gets a visible diagnostic.
4. Show enough local profile information to select the correct account. Pin the normalized root and account ID in the profile config. Before any mutation, verify final paths and file identities against the selected root and profile. Reject unexpected reparse points, path traversal, runtime root changes, and unvalidated UNC or removable destinations. Scope the lock, ownership ledger and backup manifest to the profile.

## Shortcut ownership and launch

Use a persisted binding from the game’s stable canonical identity and launch variant to a shortcut token and an assigned Steam ID. Keep token and ID stable across display-name changes, library moves, artwork replacements, game reinstalls and updates to launch arguments. Compute an interoperable candidate ID for a new binding with the documented SRM CRC convention, check its unsigned bits against every existing and planned record, and report collisions. Test whether Steam accepts deliberately assigned alternate high-bit IDs before enabling a deterministic collision allocator or multiple entries with the same literal dispatcher and title. When those compatibility cases fail, surface the conflicting row and allow a distinct display name. Reusing an ID alone never proves ownership.

When supported, write the owned shortcut with `Exe` pointing to a stable, absolute dispatcher executable, `StartDir` set to the validated dispatcher directory, and `LaunchOptions` containing a single versioned opaque token. Keep provider, game identifier, working directory and arguments in the application record. Load the approved record locally using the token. Use a directly passed application path and a correctly quoted argv string for executable actions. Use an explicit allowlist of schemes and provider-generated IDs for URI actions. Treat launch records as executable intent and check the target still matches the approved action. Return a failure for missing tokens, executables, stale source data or unsupported launch modes. Check documented Windows quoting and argument limits with a fixture harness. [Microsoft CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) · [Microsoft CommandLineToArgvW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-commandlinetoargvw)

Store target kind, normalized path, argv, working directory and dispatch policy separately. A wrapper may wait on an owned child process handle to improve Steam’s lifetime tracking for a direct child. Use bounded, provider-specific detection for a tested launcher handoff if needed. Avoid process-name-only waiting and keep launches independent of the sync UI. For a URI handoff with no trustworthy game process, report launch requested without promising overlay, controller routing, time tracking or install state. A normal shortcut offers Steam’s **Play** action, which can open an authorized store action if support is later enabled. Native install buttons and true Steam ownership are outside the MVP. Validate process tracking, Steam Input and Overlay on representative direct and store paths before listing them as supported.

Read the current VDF as an ordered typed tree. On substantial changes, preserve untouched records and their raw payloads, preserve unknown supported fields and ordering, and change only the approved owned fields. Match known names case-insensitively while retaining their input spelling. Reject conflicting aliases or malformed or unsupported data when the codec cannot preserve it safely. A missing file can initialize a new document for a validated profile. A truncated, malformed, or unreadable file blocks Apply. Distinguish signed VDF app ID bits, unsigned grid and collection ID, 64-bit shortcut game ID, and a genuine Steam AppID throughout the API.

Keep an application ledger with profile, canonical identity, token, assigned ID, last-written ownership evidence, managed filenames and hashes, and optional collection membership writes. Establish ownership from the ledger plus current evidence such as the dispatcher token and expected ID. Leave unmanaged entries untouched. For a verified managed binding with user edits, preview field-level conflicts and require explicit approval for repair or deletion. Compare user edits to the previously applied fields and present conflicts. Prune only confirmed project-owned shortcuts and unchanged project-owned assets on explicit removal or approved deselection. Follow source availability so a missing drive or failed scanner can be reported without proposing wholesale deletion.

## Apply, recovery and restart

1. **Prepare a plan.** Capture the selected profile, prior ownership state, source snapshot and fingerprints of all touched files and directories. Stage downloaded art in cache before Apply. Preview which planned actions share a transaction and which optional features are unavailable.
2. **Fence the writer.** Take an interprocess lock per normalized root/account and a short application-wide Steam lifecycle lock if requesting a shutdown or restart. Confirm Steam is fully closed before opening write targets. Ask the user to exit normally, or run a separately confirmed graceful shutdown through that root’s `steam.exe` and wait for the selected client to exit. Process queries that fail, new Steam processes, locked files, changed fingerprints, or differing filesystem identities block the write. The lock serializes Sync2Steam instances. Filesystem guards also handle other tools and concurrent Steam activity.
3. **Stage and verify.** Render patches against the fresh snapshot. Create sibling temporary files on the same volume, flush their data and re-read them. Parse staged VDF and JSON and compare the expected record/membership deltas. Validate any absent target as well as existing content. Restore original attributes and permissions where required. An unchanged profile produces zero Steam writes.
4. **Prepare durable recovery data.** Make an immutable per-apply backup of touched originals and a journal recording profile, relative target paths, old/new hashes, backups, staging names, which files were originally absent, intended operation, prepared ownership ledger and durable decision state. Verify backups and flush before publishing the first target. Keep backup contents private to the user.
5. **Commit.** Recheck the Steam process fence, paths and hashes before each replacement. Use same-volume atomic replacement for a single file with Windows rename/replace primitives. For a new file require a still-absent destination. Write replacement assets first, then shortcuts and supported collection changes, then publish the ledger. Delete obsolete project-owned files only by an exact path and expected hash and journal the deletion. Verify target bytes after each action. Preserve next/prior states in the journal so a crash before the per-file status update is recoverable from hashes. Record the verified transaction as committed once all intended target and ledger states are present. [Microsoft ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)
6. **Recover and optionally restart.** Under the same fences, inspect unresolved journals before accepting new writes. Match live files against prepared old/new states, including absent targets. A transaction without a durable commit decision normally rolls back, restoring only matching after-images. A committed transaction completes required bookkeeping, then only cleans up staging. If a third-party change or unknown file state appears, stop automatic recovery, retain all artefacts and offer a reviewed recovery plan. An explicit later rollback compares the live hashes to the transaction’s installed hashes before restoring or deleting anything. Offer restart only after verified commit or successful recovery and distinguish restart failure from commit failure.

One Steam-visible operation spans independent files. The recovery protocol provides detectable and repairable partial writes with Steam stopped. Normal reader locks and Windows per-file replacement cannot remove every race with external processes. Hold filesystem identities and use the narrowest supported sharing and replacement checks, fail closed when invariants cannot be shown, and exercise race and power-loss behavior through injected failures. Retain manifests and verified backups for the documented recovery window.

## Collection compatibility

Record intended collections in the plan and ledger and optionally reflect them as shortcut tags. Use a versioned adapter only for the tested Steam cloud-storage JSON records. Read and validate namespace declarations and candidate collection records. Namespace versions belong to their own namespaces. Require a uniquely identified, structurally valid collection namespace for writes, or leave intended collection changes pending with an explanation. A known initialized empty-namespace path requires client evidence before it becomes a supported write target. Keep other cloud records and collection envelope fields intact.

Generate deterministic project-owned collection IDs in an application namespace. Preserve user collections, custom names, unrelated members, unknown fields and tombstones. Apply updates only to known owned records or an explicitly adopted membership and retain the base state for conflict detection. Use unsigned shortcut IDs for memberships. Reconcile removals using prior ownership and ignore unsupported or dynamic filters. Run the collection adapter through the same backup, precondition and recovery path as shortcuts. After a validated Steam restart, report whether the client rendered the requested collection. Offline, a written collection has pending online reconciliation. If Steam’s format or behavior changes, disable collection writes for that layout and retain shortcut and artwork support.

Use optional static collections named **Sync2Steam · Installed** and **Sync2Steam · Not Installed**, with an optional **Unknown** group for inconclusive scans. Names are editable; track IDs independently. Classify the selected launch source. A forced uninstalled copy can legitimately appear under Not Installed. On startup refresh local observations asynchronously or let the user refresh manually. Publish memberships only during reviewed sync with Steam closed. Launch-time checks may update a local observation, never Steam files. Defer Task Scheduler because unattended writes introduce stale-preview and client contention risks. No real-time Steam install indicator is available.

## Artwork matching, cache and install

1. Prefer a user-supplied asset or explicit match override, then the last confirmed SteamGridDB game ID. Eligible native Steam catalog titles can be matched with their genuine AppID. Use a verified supported external platform ID for other store lookups when available. Otherwise search by sanitized title and reviewed edition, platform, year or source hints. Preserve the original display title and game identity. Ask the user to choose when editions or names are ambiguous. A known-good existing artwork slot wins over empty candidates and a provider failure.
2. Keep SteamGridDB opt-in. Store a user-supplied key with current-user Windows credential protection. Use it for HTTPS requests to SteamGridDB’s API only. Search transmits a title or explicit catalog ID. Never send paths, command lines, Steam profile metadata or local identities. Do not attach the bearer token to asset downloads or cross-origin redirects. Use bounded concurrency, timeouts, cancellation and retry/backoff, honoring `Retry-After` when present. Classify offline, credentials rejected, throttled, temporary error, game absent and slot absent separately.
3. Cache the confirmed match, image IDs and metadata, actual asset bytes, content hashes and fetch/revalidation metadata. Include media variant and relevant filter settings in cache lookup keys. Retain immutable content-addressed bytes when settings change and keep the user’s selected slot mapping stable. Cache no-match briefly, distinguish network failures from negative results, and let users correct matches without renaming the Steam shortcut. Offline mode uses verified cached bytes or explicit local assets with no API calls.
4. Download and decode assets away from Steam, with size/dimension limits, format sniffing and an allowlist of supported image types. The proposed baseline is static PNG/JPEG with PNG transparency for logos and an explicitly tested PNG/ICO route for icons. Keep the filename extension consistent with the decoded output, reject unsupported or malformed data, validate HTTPS asset URLs against supported providers and cap redirects. Use thumbnails for browsing and stage the selected full-resolution image.
5. Map validated bytes to the corresponding stems in [Steam research](../research/steam.md#artwork-placement-and-steamgriddb), including an absolute icon reference only if the asset is part of the plan. Keep existing logo layout and any unmanaged grid art. Treat conflicting stems using several extensions as an explicit conflict. Set a default logo layout and landscape alias only after confirming the supported client needs them. Journal any owned overrides and follow the same ownership checks for replacement, cleanup and rollback.

## Dispatcher and artwork defaults for the first trial

Use the same executable's headless dispatch mode from a user-chosen durable path. A portable copy on removable storage can disappear. Show the pinned path at publication, preserve it on update and offer a previewed rebind after relocation. Never silently copy a helper into autostart or recreate all bindings. Until a disposable client confirms continuity, warn that a relocation can disrupt Steam Input and art associations.

| Observed state | Dispatcher result |
|---|---|
| Installed with verified action | Launch the selected product through its validated original launcher or supported local GOG task. |
| Absent | Use verified install handoff, else an identified product page or launcher library. Label the actual destination. |
| Installing | Open the client's status/library view when supported; avoid a second install request. |
| Unknown | Rescan this product once. If still unknown offer its verified client page or an actionable error. |
| Launcher missing or auth expired | Explain the missing requirement. Offer an allowlisted official download page or the provider's sign-in experience; never download and execute an installer. Keep a forced source selection. |

Start with static art, an appropriate aspect ratio and manual per-slot pinning. Add style, language or animation filters only when the upstream fields support them. Do not equate provider ranking with official publisher art. Preserve user logos and their position. Bound disposable cache storage and measure a representative artwork workload before setting its cap and eviction policy. The five slots can approximate native presentation but do not create achievements, native ownership, store association or native install management.

## Acceptance evidence

| Surface | Synthetic or isolated validation required |
| --- | --- |
| Discovery | Mock registry views, custom root, multiple profiles, missing and malformed login metadata, inactive profile, path aliases and reparse points |
| VDF and reconciliation | Round-trip casing, signed and unsigned IDs, non-ASCII paths and names, unknown fields and order, tags, duplicate or malformed data, missing files, edits after preview, collisions, idempotent Apply and removal of owned entries only |
| Transactions | Mock running Steam, restart during commit and competing writers, sharing violations, crash before/after each replacement and journal write, absent-path restoration, partial backup failure, external edits during recovery |
| Launch | Fake executable asserting exact argv and CWD, missing or stale tokens, Unicode/spaces/backslashes, allowed URI paths and handoff, overlay/lifetime/Input matrix on a later authorized client |
| Collections | Synthetic namespaces with unrelated high versions, malformed rows, multiple candidates, duplicate names, tombstones, dynamic and unrelated entries, then offline and online reconciliation on a later authorized client |
| Artwork | Mock HTTP success/errors/429, no-key and offline, duplicate titles, invalid or large image, partial download, existing custom art, distinct ID representations, each grid slot and desktop/Big Picture rendering on a later authorized client |

Begin with fake roots and a mock artwork provider. Any future live compatibility trial needs a purpose-built disposable Windows profile and explicit authorization for the Steam client and account. Capture the Steam build and channel, write-set diffs and visible results so a client update can be assessed against known behavior.
