# Desktop UI standards

Proposed for the Windows-first Sync2Steam application. The layout and performance targets are implementation criteria to validate with the first native build. The [GPUI research](../research/gpui.md) records the candidate toolkit and its Windows test coverage.

## Navigation and task flow

Use one main window with a labeled left navigation rail and a content pane. Open on Library. Keep the current view, the latest relevant status, and the next available action visible. Use the system title bar in the first implementation. At narrower widths, collapse navigation to a labeled menu and prioritize title, selected source, and action columns. Preserve access to secondary columns in expanded rows or details.

| View | What the user can do |
| --- | --- |
| **Library** | Search and sort titles, filter by source, and isolate ambiguous duplicates. Each collapsed row shows the title, copy count, selected launch source, and any unresolved status. Expanding a title reveals editions and source copies with store/account label, installation state when known, and the effective choice for that title. The row detail is where users set or clear a per-game override. |
| **Accounts** | Connect or disconnect supported accounts, refresh a source, and see which data is available. Show a source’s last successful refresh, ongoing work, and actionable errors in the source row. An account that needs attention leaves the other sources usable. |
| **Sync Preview** | Review the pending Steam changes against the chosen Steam user before applying. Show counts and rows for additions, updates, unchanged shortcuts, and any conflicts or removals the plan contains. Keep unresolved items visible with their reason. Show the effective source and the rule or override that selected it. Disable Apply for a stale or blocked plan and explain how to refresh or resolve it. Reveal completion and failures persistently on this view. |
| **Settings** | Change global store priority and the installed-first preference. Explain their effective relationship with per-game overrides using the actual selection rule and show the resulting preferred source in Library and Sync Preview. Provide keyboard-operable move-up and move-down controls for priority. Show the selected Steam destination where the application permits changing it. |

Group rows by the domain’s resolved title identity. Keep uncertain matches visible without silently folding distinct editions together. Counts refer to copies in the group, including off-screen child rows, and update with the underlying data. Provide a short explanation beside each exception so the user can distinguish an ambiguous match, a disconnected source, and an unavailable launch target. Use explicit state such as “Installation unknown” when the provider cannot establish it. Preserve the search and filter state and the selected title when switching between Library and preview or refreshing data. If that title disappears, move focus to the nearest visible row or the search control.

The virtualized table is the primary Library view. A cover grid is optional and uses the same selection, filters, effective launch choice, and copy counts. Reserve image dimensions, lazy-load visible covers, and fall back to a readable title treatment for missing art. The table stays immediately usable when covers are unavailable.

## Visual and interaction standards

- Use shared semantic tokens for surface, text, border, accent, focus, selection, and status. Follow system light and dark preference and verify Windows contrast themes. Use one accent for primary actions and labels or icons alongside every meaningful status color. Use 4.5:1 contrast for ordinary text and 3:1 for large text and controls or essential graphics as project criteria. [Microsoft Windows app practices](https://learn.microsoft.com/en-us/windows/apps/get-started/best-practices) · [WCAG text contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [WCAG non-text contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast)
- Use the installed Windows UI font with sensible fallback. Start with 14 logical px body and table text, 20 logical px screen headings, and a 4 logical px spacing grid. Start with 36 logical px default rows and 32 × 32 logical px action targets. Let text and containers grow for larger text and wrapped labels. Verify a 900 × 600 logical px client area, 100%, 125%, 150%, and 200% display scaling, and 200% system text scaling. Test long game titles, localized strings, and monitor changes.
- Use hierarchy through typography and spacing. A compact Library row favors title, copy count, and effective source. Give secondary information a single clear place in the expanded row or details. Keep overlays for focused confirmations and related edits. Keep background jobs, errors, and recovery actions in the originating view. Reserve transient notifications for brief, nonessential feedback.
- Tab and Shift+Tab traverse the rail, toolbar, content, and footer in reading order. Use arrows within a table or composite. Enter activates the focused row or control, Space toggles checkboxes, and Escape closes menus and dialogs or returns focus from details. `Ctrl+F` moves focus to Library search when that view is active. Use a visible focus ring and restore focus to the invoking control after dismissing an overlay. In a confirmation with irreversible effects, focus the safe action first. Provide every reorder and row affordance through keyboard and assistive actions. [GPUI Kit focus](https://gpui-kit.com/docs/focus/) · [GPUI Kit keybindings](https://gpui-kit.com/docs/keybinding/)
- Give interactive controls names and roles, with selected, expanded, checked, and enabled state where the platform exposes them. Use domain-keyed IDs for repeated rows. Expose meaningful table cell labels, announced group counts, and changes to salient status. Group expansion must announce the expanded state, and recycled rows must preserve selection and identity across sorting and filtering. Maintain a single command path for pointer, keyboard, and assistive actions. Validate focus and UI Automation behavior with Accessibility Insights and complete the core workflows using Narrator. [GPUI Kit accessibility](https://gpui-kit.com/docs/accessibility/) · [DataTable accessibility](https://gpui-kit.com/component/data-table/#accessibility) · [Accessibility Insights Inspect](https://accessibilityinsights.io/docs/windows/getstarted/inspect/)
- Render from local view state. Read storage, fetch provider data and images, and perform expensive indexing, sorting, and preview computation off the UI thread. Apply completed results coherently and discard superseded generations. Coalesce progress invalidations, virtualize long lists, and keep selection by identity. Present cached content during a refresh where available. Stop decorative motion when reduced motion is enabled. [VirtualList](https://gpui-kit.com/component/virtual-list/) · [Kit release notes](https://gpui-kit.com/releases/)

## Performance acceptance protocol

These budgets are proposals, with no measured baseline yet. Record the first run and accept or revise the targets using observed data before treating them as release thresholds.

**Reference configuration.** Use a plugged-in Windows 11 x64 machine with a four-core or better CPU, 16 GiB RAM, an integrated DirectX 11-capable GPU with vendor driver, SSD storage, and a 60 Hz display at 125% scale. Run the packaged `--release --locked` build in a visible foreground window with fixed viewport and power settings. Document OS build, machine, driver, app and dependency revisions, build profile, window size, scale, refresh rate, and tool versions. Keep tests scripted and capture absolute timings and input sequences. Apply the same script to the supported Windows baseline and 200% scaling as separate runs.

**Dataset.** Keep a versioned deterministic fixture of 10,000 canonical titles and 20,000 copies across four provider IDs, including variable-length names, installed and unknown data, duplicate candidates, overrides, and nontrivial preview output. Include ambiguous group sizes from two to eight. Add an empty first-launch fixture, a representative 1,000-title fixture and a 50,000-copy stress fixture. Use seeded local thumbnail assets only for a separate optional cover run. Use captured fixtures or deterministic fakes for sources so network jitter and credentials stay out of the UI baseline. Run an additional pass with throttled refresh and active preview computation to test responsiveness.

| Scenario | Measurement | Proposed threshold |
| --- | --- | --- |
| Cold and warm startup | From process launch to interactive first frame of Library with a visible row or empty state. Correlate launch marker and first qualifying presented frame. Collect ten cold launches after reboot or a recorded equivalent cache reset and twenty warm launches after clean process exit. Record p50 and p95 for empty and cached reference fixtures. | Cached cold p95 ≤ 1.5 s and warm p95 ≤ 750 ms. |
| Open or expand a nearby row, switch views | From enqueueing the scripted input to the first presented frame with the requested detail or the next view’s actionable shell. Collect at least 30 operations for each scenario. | Each p95 ≤ 100 ms. |
| Search, filter, and sort | From final test input, including debounce, to the first presented frame containing the correct local projection. Use 30 preselected queries covering common, sparse, ambiguous, and empty matches. Include toggling the ambiguity filter and changing sort. | Each p95 ≤ 250 ms for the 10,000-title fixture. |
| Sync preview | Measure time to first visible busy state and then to the complete displayed local plan, using the same canonical fixture and local Steam target state. Collect 20 plans and keep cache conditions consistent. | Busy feedback p95 ≤ 100 ms. Usable preview p95 ≤ 2 s. |
| Continuous scroll | Script repeatable wheel or scrollbar movement in a section with extended scroll range. Collect three 30 s trials at 60 Hz and inspect the actual app swap chain during active scroll. Report frame-interval p50/p95/p99 and dropped-frame rate for each trial, including a run with refresh in progress. | Interval between displayed app frames p95 ≤ 20 ms, p99 ≤ 34 ms, and missed 60 Hz display slots ≤ 5%. |
| Idle and memory | After 60 seconds of settling on the 10,000-title table, sample app process-tree CPU and private working set every second for 120 seconds. Use whole-machine CPU percentage and report the highest one-second sample alongside the mean. Repeat after twenty filter/expand/collapse cycles and record the settled working set. | Mean CPU ≤ 1% and settled private working set ≤ 200 MiB. After cycles, settled increase ≤ 20 MiB. |

Use Windows Performance Recorder and Analyzer for ETW CPU, disk, memory and scheduling traces and a pinned PresentMon release for display-change intervals and present metadata. The scroll missed-slot metric counts extra refresh periods between displayed app frames within active scrolling windows, divided by all refresh slots in those windows. Keep dropped presents as a separate diagnostic. Correlate input and view markers with the displayed frame, or use synchronized capture if the tooling cannot establish the match. Record any failed scenario or missing trace as such. Use nearest-rank percentiles and retain raw traces, fixture version, and command details so the first baseline can be reproduced. [Microsoft ETW tools](https://learn.microsoft.com/en-us/windows/win32/etw/event-tracing-tools) · [Intel PresentMon](https://github.com/GameTechDev/PresentMon)

Use the representative screen and acceptance checks in the [Windows UI gate](../../docs/roadmap.md#windows-ui-gate) for toolkit selection. As each feature lands, extend coverage to source overrides, account recovery, priority reordering and preview through Apply against disposable data. Exercise pointer, keyboard, and Narrator paths, capture normal and contrast-theme screenshots, and confirm that large-list selection remains valid when the visible rows are recycled. Run the same key state and action cases in the Kit integration harness where they are observable. [GPUI Kit testing](https://gpui-kit.com/docs/test/)
